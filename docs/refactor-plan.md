# 架构评估与重构方案

> 目标：判断「Rust / Go / 保留 C++ Qt 继续优化」哪个是最优路线，并给出可执行的迁移方案。
> 评估依据：`docs/reverse-analysis.md` 的实测证据 + 本机真实构建验证 + GitHub 同类项目横向对比。
>
> **版本说明**：本文是 **v1.0.0 阶段**的选型论证（Rust + 手写 Win32 FFI），
> 文中「418 KB 产物」等体积数字属于该阶段。后续 **v2.0.0** 将前端换成 Tauri 2 + WebView2，
> 但「Rust + 纯逻辑 core 层 + 单二进制交付」的结论未变，core 层被原样保留为
> `tauri/reminder-core`。本文保留为决策记录。

---

## 1. 结论

**改用 Rust（`x86_64-pc-windows-gnu` + 手写 Win32 FFI + 纯逻辑 core 层）。**

三条决定性理由，按权重排序：

| # | 理由 | 可验证事实 |
|---|---|---|
| 1 | **UI 框架是全部复杂度和体积的来源，而本程序不需要它** | 原程序 15.93 MB 中自有代码仅 106 KB（199 函数）；换成 GDI 自绘后产物 418 KB，**降 97.4%**，功能不减 |
| 2 | **Go 的最低体积门槛不可接受** | Go 静态链接必然携带 runtime + GC，同类托盘工具实测 5~10 MB；Rust 无 GC 无 runtime，本机实测 418 KB |
| 3 | **继续用 C++ Qt 无法解决真正的病根** | 病根是 `TaskDialog` 单函数 11.2 KB、表单状态存在控件里、`+0x44` 字段联合复用。这些与语言无关，但 Qt 的信号槽 + 手写偏移结构体让它们更难拆；Rust 的 `enum + match` 强制穷尽，重构收益更大 |

**保留项**：原程序做对的地方全部保留 —— 12 种调度枚举、`QSaveFile` 式原子写、`idle >= 300s`
重置使用计数、单实例互斥、`--silent` 静默启动、托盘文案。

## 2. GitHub 同类项目横向对比

检索到的可参照项目（均为 Rust/Go 桌面提醒类，2026 年在维护）：

| 项目 | 技术栈 | 与本项目的关键差异 | 可借鉴点 |
|---|---|---|---|
| `adoin/Schedule-Manager` | Rust + **Slint** + SQLite | 有云端同步、农历、月历挂件 —— 远超本项目范围 | 六类发生规则的分层建模；托盘三态关闭行为（最小化/隐藏/退出）持久化 |
| `dcwon/desk-note` | **Tauri** + TS + Rust | 便利贴形态，WebView 前端 | 「窗口不进任务栏」的标志位组合；数据落 Tauri app data 目录 |
| `kaima2022/health-reminder` | **Tauri 2.0** + Vite + Vanilla TS | 久坐/喝水/护眼/强制锁屏，与本项目功能重合度最高 | **空闲检测暂停久坐计时**（与本项目 `idle>=300s` 同思路）；严格模式隐藏解锁按钮 |
| `tinydream96/KID-reminder` | Tauri 2.0 + Rust | 同类，含多显示器锁屏 | 推迟次数上限防无限拖延；提前 5 秒预告（避免打断正在保存的工作） |
| `huanfeng/wind-ui-rust` | **纯 Rust + Win32/GDI 自绘** | 是 GUI 框架本身，不是应用 | **与本方案技术路线完全一致**：无 runtime 无 GC，Win32+GDI 直绘，实测最小窗口 0.44 MB / 私有内存 3.65 MB —— 佐证「Rust + GDI」能达到的量级 |

**对比结论**：

- 主流同类项目两条路线：**Tauri**（Web 前端，体积 20~70 MB）与 **纯原生 Rust + 自绘**（<1 MB）。
- 本项目 UI 极简（一个列表 + 一个表单 + 一个卡片弹窗），**上 Tauri 是负优化**：引入 WebView2 运行时、
  IPC、前端工具链，换来的是本项目根本用不到的富文本能力。
- `wind-ui-rust` 的实测数据（0.44 MB / 3.65 MB 私有内存）与本机实测（418 KB / 12.2 MB 工作集）
  数量级一致，说明路线选对了。

## 3. 三方技术选型取舍

### 3.1 评分表

| 维度 | Rust（选定） | Go | 保留 C++ Qt |
|---|---|---|---|
| 产物体积 | **418 KB** ✔ 实测 | 5~10 MB（runtime+GC 不可剥离） | 15.93 MB（Qt 静态） |
| 运行时依赖 | **0** ✔ | 0（但含 runtime） | 0（Qt 静态） |
| 常驻内存 | **12.2 MB** ✔ 实测 | 20~40 MB（GC 堆） | 约 30~50 MB（Qt 静态库映射更大） |
| 空 CPU 占用 | ✔ 事件循环阻塞 + 4s 定时器 | 尚可 | ✔ 同 |
| Win32 互操作 | 零成本 FFI ✔（但需自写声明，见 §4.2） | cgo 有开销；`syscall` 包覆盖不全 | 原生 ✔ |
| 状态建模能力 | **`enum` + `match` 穷尽检查** ✔ | 接口 + type switch，弱 | 虚函数 + 手写偏移，最弱 |
| 重构原病根（巨型函数/状态散落） | **收益最大** ✔ | 中等 | 低（易延续原结构） |
| 编译速度 | 慢（本机 42s release） | 快（秒级） | 中 |
| 学习/维护门槛 | 高（借用检查） | **低** ✔ | 高（Qt 生态 + C++） |
| 本机可构建性 | ✔ 已验证 | ✘ **未安装 Go 工具链** | ✘ **未安装 MSVC/Qt** |

### 3.2 为什么不选 Go

1. **体积门槛**：Go 二进制必然包含 runtime、GC、调度器。实测同类工具 5~10 MB。对一个「托盘小工具」
   而言，418 KB 与 8 MB 的差别用户在下载/分发时能直接感知。
2. **UI 仍是死路**：Go 原生 GUI 只有 Fyne（自绘，风格不原生）、Wails（WebView）、walk（Win32 绑定但已
   半停滞）。要做出本项目的原生观感，最终仍要落到 Win32 调用，而此时 cgo 的开销与封装的绕弯
   （引用搜索结果原话：「winapi 封装略绕」）不如 Rust 的零成本 FFI 直接。
3. **状态建模弱**：本项目的核心价值在 12 种调度的时间运算正确性。Go 的接口/类型断言做不出
   Rust `enum` 那种「新增变体必须处理所有分支」的编译期保证，而这正是原程序 `+0x44` 字段复用
   出错的根源。
4. **本机无工具链**：未安装 Go，验证成本更高。Rust 已在本机完成构建 + 69 项测试 + 运行验证。

### 3.3 为什么不保留 C++ Qt

保留路线看起来最省事（改动最小），但算总账最贵：

| 项 | 代价 |
|---|---|
| Qt 版本锁定 | Qt 5 已停止开源维护，升级 Qt 6 要改 `QString`/`QVector` API、`QRegExp`、信号槽语法 |
| 分发 | 15.93 MB 单文件；若改动态链接则要带一堆 DLL 与插件目录 |
| 原病根不解决 | `TaskDialog` 11.2 KB 巨型函数、表单状态塞控件、`+0x44` 联合复用 —— 这是架构问题，换语言才有动机重写 |
| 本机无 Qt 环境 | 本机未安装 Qt 与 MSVC，无法验证构建 |
| 收益 | 只能省下「重写」的一次性成本，但后面每次改动都在还利息 |

> **反过来说**：如果这个项目每月都要加新调度类型、要接日历同步、要做多语言，Qt 的成熟度确实值钱。
> 但本项目 12 种调度已覆盖需求，属于**功能冻结的稳定工具** —— 这类项目的最优解是「一次性重写成
> 最小依赖 + 长期零成本维护」，而不是「留在重型框架里持续付框架税」。

### 3.4 若坚持跨平台（未采纳）

若未来需要 macOS/Linux，路线会变成 **Rust + winit/tao + 平台抽象**，core 层可 100% 复用
（本项目 core 层已零平台依赖，可原样编译到任意 target）。这也是选 Rust 而非 Go 的隐藏收益：
core 的复用边界最干净。

## 4. 重构方案

### 4.1 分层设计（对应原程序的架构缺陷）

```
┌─────────────────────────────────────────────────────┐
│ main.rs        消息循环 / tick 编排 / 托盘命令分发   │
├─────────────────────────────────────────────────────┤
│ platform\      Win32 适配（9 个模块，唯一 unsafe 区） │
│   ffi  tray  autostart  idle  audio  window          │
│   manager  newtask  single_instance                  │
├─────────────────────────────────────────────────────┤
│ core\          纯逻辑，零 Win32，可单测（69 项）      │
│   time   日历运算（替代 QDateTime，无 chrono 依赖）   │
│   model  12 种 Schedule 枚举 + Task                  │
│   scheduler  next_trigger + 触发状态机               │
│   engine     tick 循环 + 使用时长累计                │
│   store      JSON 持久化 + 原子写                    │
└─────────────────────────────────────────────────────┘
```

**关键改进（逐条对应原缺陷）**：

| 原缺陷 | 原程序 | 本实现 |
|---|---|---|
| 12 种调度塞进 1 个 11.2 KB 函数 | `0x9d00` | `Schedule` 枚举 + 12 个独立 `match` 分支；新增类型编译器强制补全 |
| 表单状态存在 UI 控件里 | `0xcb10` 直接 `[rsi+0x38]` 读控件 | `DialogResult` 结构体，UI 只做 I/O |
| `+0x44` 字段被两种调度复用 | `pomodoroWorkMinutes` / `startupDelayMinutes` 同偏移 | 枚举变体各自持字段，物理上不可能混用 |
| `version` 只写不读 | `0x1af20` 写 version，`0x1a930` 不校验 | `load()` 遇 `version > SCHEMA_VERSION` 直接报错不覆盖 |
| 无单元测试 | 无测试框架符号 | 69 项测试，覆盖 12 种调度的边界（闰年/月末/周末/跨年/番茄钟全周期） |
| 业务逻辑依赖 Qt 类型 | `QDateTime`/`QTime`/`QVector` | 自实现 `DateTime`/`TimeOfDay`，可脱离平台测试 |

### 4.2 本机工具链障碍与解法（实测记录）

| 障碍 | 现象 | 解法 |
|---|---|---|
| `windows` / `windows-sys` crate 不可用 | `error: error calling dlltool 'dlltool.exe': program not found`；加 self-contained 后仍报 `dlltool: CreateProcess` | **手写 73 个 `#[link]` 声明**，直接链接 GNU target 自带的 `libuser32.a` 等预编译导入库 |
| `serde_derive` 过程宏编译 | 同样依赖 dlltool | 构建时前置 self-contained binutils 到 PATH（见 `docs/build.md §3.2`） |

> 这两条不是「绕过问题」，而是本机环境的客观约束。产出结果：**依赖面从「windows crate 全家桶」缩到
> 手写 73 个声明**，反而更可审计。

**未实现（有意裁剪，非遗漏）**：

| 原功能 | 原因 |
|---|---|
| 自绘日期时间选择器（`PopupDateTimeEdit`/`InlineTimePicker`） | 纯视觉增强，改用文本输入 + 明确格式提示，功能等价且代码量从 3 个类降到 0 |

### 4.4 迁移步骤（可复现）

```
1. 取证         静态解析原 exe（PE/Qt 元数据/RTTI/pdata/字符串/跳转表）→ docs/reverse-analysis.md
2. 抽规格       把行为写成规格：12 种枚举语义、next_trigger 算法、状态字段、持久化 schema
3. 净室实现     core 层（纯逻辑）→ 单测先行，69 项覆盖边界
4. 平台层       手写 Win32 FFI → 逐模块（tray/autostart/idle/audio/window/manager/newtask）
5. 缝合         main.rs 消息循环 + tick 编排
6. 验证         构建 / 单测 / 进程常驻 / 单实例 / Win32 调用链（examples/diag）
7. 品牌清理     LICENSE + 19 个文件头版权标注；全仓 grep 确认零原作者痕迹
```

### 4.5 净室声明

本重构**未复制原程序任何代码**。原程序为 MSVC 编译的机器码，未做反编译源码还原；重构实现依据的是
**行为规格**（观察到的调度语义、字段语义、字符串文案），独立用 Rust 编写。
原程序的作者信息与关联站点已在源码中完全清除（仅在分析报告中作为证据引用保留 1 处）。
